一、这个项目是怎么来的
我们的系统由很多微服务组成，每个微服务都会调用各种第三方 API——短信、三要素、四要素、OCR、受益人……随着接入的服务越来越多，我发现一个问题：没有一个地方能统一告诉我，谁在调用什么接口、调了多少次、有没有快超配额了。
每次想搞清楚这件事，要么靠人工问、要么翻各个服务的日志，效率很低，而且看不全。
于是我做了一个叫**观测中枢（WatchHub）**的工具，来解决这个问题。这次特别的地方在于：整个产品，从需求到上线，我用 AI Agent 完成了开发。
在分享这个过程之前，我想先说一件事：这一次做得很快，但这不代表大家也必须一样快。 条件不同、环境不同、功能不同、情况不同——很多都不同。不会因为自己这一次变快了，就要求大家也必须跟上。这只是一次真实的过程记录和经验分享，没有任何压力传导的意思。

三、我观察到的研发瓶颈
在讲这次的做法之前，我想先说说我观察到的一个长期存在的问题。
在分账开发、宁小奢 APP 开发过程中，我看到：沟通成本是我们最大的障碍。
研发做得流不流畅，根本上取决于研发对业务理解的深不深。
分账是重业务的产品，宁小奢 APP 也是——绝大部分页面和功能都围绕着业务逻辑。如果研发对业务不熟悉，面对每一个页面、每一个功能点，他都不知道为什么产品要这么设计。不知道"为什么"，他就不知道"怎么实现才是对的、哪里会出问题"。
就算他在某一个点上去问产品，产品给他解答了这一个点，他还是串不起来——因为理解是碎片化的，不能举一反三，下一个问题还是要再问。
需求变更：最受伤的是后端。没有规律没有原则的“变更”、底层指导思想的“变更”，对后端全盘逻辑往往是颠覆性的。
核心矛盾在这里：业务理解要靠沟通来传递，而沟通本身成本极高、效果不稳定。 说的人觉得自己讲清楚了，听的人不一定真的理解了；理解了当下的，不一定能迁移到其他场景。
这不是任何人的问题，是信息传递本身就有损耗。

四、为什么这次能做这么快
这次之所以快，有四个原因。
第一：零沟通成本。
全程只有我一个自然人参与。没有产品和研发之间的对齐，没有前后端之间的联调沟通，没有研发和测试之间的 bug 扯皮，没有等待，没有信息传递的损耗。
第三节说的那个根本矛盾——业务理解要靠沟通传递——这次直接就绕开了。因为只有我一个人，我既是出需求的人，也是做决策的人，也是验收的人。
第二：产品一镜到底。
第一版 PRD 出来之后，没有变更过。从产品设计到开发完成，需求是稳定的。
产品需求的变更，是研发返工最大的来源之一。这次没有这个问题。
第三：几乎没有返工。
开发快，不是因为打字快，而是因为几乎一步到位。
根本原因是：有一份高质量的 PRD 文档作为基石。 这份文档让 AI 在每一步都有清晰的方向——知道要做什么、为什么这么做、边界在哪里。不用猜，不用试错，不用做到一半发现方向不对再推翻重来。
这三点合在一起：没有沟通损耗、需求不变、不返工——速度自然就上来了。
第四：没有测试给我提bug
修bug，哪怕让AI修bug，短则几分钟，如果还要排查一下，检查一下，二十分钟很容易就消耗了。

六、多智能体协作模式
这次我用了四个 AI Agent，分别扮演不同的角色：

- 产品经理 Agent：负责理解需求、形成 PRD、维护需求边界
- 前端架构师 Agent：负责技术选型、页面架构、组件设计
- 后端架构师 Agent：负责 API 设计、数据库建模、巡检调度机制
- 测试工程师 Agent：负责接口自动化测试、测试用例设计
  为什么是四个，而不是让一个 Agent 做所有事？
  因为不同角色需要不同的上下文和不同的思维方式。产品经理关心的是"用户要什么"，后端架构师关心的是"怎么设计才稳"，测试工程师关心的是"哪里最容易出问题"。把这些混在一个 Agent 里，它不知道该用哪个视角思考，容易产生角色混乱。
  每个 Agent 有一份"入职说明书"（CLAUDE.md）。
  这是一个放在对应目录下的文件，里面写清楚了：这个 Agent 是谁、它的职责是什么、它需要遵守哪些原则、它的主要产出物是什么。每次在对应目录下启动 Claude Code，它就会自动加载这份说明书，进入对应的角色状态。
  我在这个过程中扮演的角色，不是开发者，而是指挥者。
  负责提需求、做决策、协调各角色之间的信息传递、最终验收。具体的方案生成、代码编写、文档产出，都由 Agent 完成。

七、产品设计阶段：推与拉
在和 AI 探讨产品设计时，我总结出两种模式。
推模式：你推着 AI 走。
把你的想法告诉 AI，让它帮你实现、完善、表达。好处是对齐快，你的意图能直接落地。但上限是你自己想法的深度——你想得有多深，产品就有多深。一个没有产品经验的人把他的想法推给 AI，AI 能帮他实现，但想法本身的质量 AI 改变不了。
拉模式：让 AI 拉着你走。
通过提问，让 AI 给你建议、教你怎么想、指出你可能没有考虑到的地方。你不是在给 AI 答案，而是在问 AI 问题。这种模式能打开你自己想不到的可能性，让产品的深度超过你原本的认知上限。
真正有效的方式，是推拉推拉——交替进行。
你先推出一个方向，AI 拉着你深入；深入之后你再推进一个决策，AI 再拉着你想清楚边界……整个产品设计的过程，就是在这种来回拉扯中，把一个模糊的想法变成一份清晰的、有深度的 PRD 文档。

八、开发全流程
Phase 1：产品设计（约 3 小时）
切换到产品经理 Agent，从问题出发开始对话。通过推拉推拉的方式，把需求逐步梳理清楚——采集模块怎么设计、分析维度是什么、监控规则怎么触发、数据模型是什么……最终形成一份 PRD 文档。这份文档不只是"要做什么"，还包含了"为什么要这么做"的设计原则。
Phase 2：架构设计
分别切换到前端架构师 Agent 和后端架构师 Agent，各自基于 PRD 出技术方案。后端确定技术栈（Go + Gin + MySQL）、API 设计、数据库结构、巡检调度机制；前端确定框架（React + Ant Design + ECharts）、路由结构、状态管理方案。
Phase 3：后端开发
按照架构方案，由后端架构师 Agent 完成代码编写。在接口设计阶段，已经知道每个界面需要哪些接口，所以接口设计是面向前端需求的，不是凭空设计的。后端开发完成后，部署到本地，所有接口可以真实调用。
Phase 4：前端开发
后端部署完成之后，前端才开始。前端架构师 Agent 直接对接真实的后端 API 进行开发，没有 Mock。这省掉了联调环节，前端看到的数据就是真实数据。
Phase 5：测试验证与修复
测试工程师 Agent 完成 API 自动化测试用例的编写，覆盖核心业务链路。发现问题、修复、再验证。以上四个阶段合计约 7-8 小时。
Phase 6：部署上线（约 5 小时）
部署是整个过程里最麻烦的一步。AI 能帮你写代码，但上线涉及基础设施，步骤多、环节杂，目前还是要靠人一步步踩过去：

- 前后端各自构建、打 Docker 镜像
- 配置路由规则
- 配置环境变量
- 配置域名和 SSL 证书
- 配置生产数据库
  每一步都可能有问题，排查、调整、再试。这五个小时花在这里，是真实的。

九、哪些事 AI 做得好，哪些还是要靠人
这次的体验让我对 AI 能做什么、不能做什么有了更清晰的感知。
AI 做得好的

- 方案生成：给一个方向，它能快速给出合理的技术方案
- 代码编写：基于清晰的需求和接口定义，代码质量是可用的
- 文档产出：PRD、架构文档、API 文档，都能生成
- 跨角色一致性：同一份 PRD，不同 Agent 读到的是同一份，不会像人一样各自理解不一致
  靠人判断的
- 需求的合理性：AI 会帮你把需求做出来，但需求本身对不对、有没有价值，它不替你判断
- 产品取舍：功能要还是不要、先做还是后做，这些决策需要人来做
- 最终验收：做出来的东西对不对、体验好不好，人看一眼才知道
- 部署和基础设施：这块还是要靠人
  一句话总结：AI 负责执行，人负责判断。

十、结语
这次做 WatchHub，最大的收获不是产出了一个工具，而是验证了一种工作方式的可能性。
AI 不是来替代产品、研发、测试的，而是把每个角色能做到的事情的上限往上推了。产品能想得更深，研发能做得更快，测试能覆盖得更全——但前提是人要在正确的位置做正确的事：判断、决策、验收。
这个上限能推多高，取决于你怎么用它。
